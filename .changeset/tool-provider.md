Add per-call `tools` overrides and a `ToolProvider` construct: `AgentDefinition.tools` and `AgentRunInput.tools` now both accept a plain `ToolSet` or a `ToolProvider` (`{ getTools(ctx) }` — a true interface, so a provider can be a class instance), so tools can depend on runtime context (e.g. which sandbox root a dangerous tool should use for this run) instead of being fixed at agent-definition time. Resolved once per call, merged as `{ ...runtimeTools, ...definitionTools, ...inputTools }` before `streamText`. `createToolProvider({ getTools, contextSchema? })` wraps a plain function into this shape (a config object, not positional args, so future additions don't force reordering call sites); `agent.tools` exposes the resolved value for introspection.

`combineToolProviders({ name: source, ... })` merges several **named** tool sources into one — keyed, not variadic, so the combined `toolProviderContext` is **namespaced**: `agent.run({ toolProviderContext: { name: ... } })`, and each source only ever sees its own slice, never a sibling's. This makes field-name collisions between independently-authored providers structurally impossible. `Tools` (the actual tool names) are still merged flatly, typed as the union of everything each source contributes.

The framework never parses or validates `toolProviderContext` — a `ToolProvider` that wants Zod validation/defaults calls `.parse()` itself, as the first line of its own `getTools`. `ToolProvider.contextSchema` is separate, optional introspection metadata (e.g. for a settings UI to build a form from), never read by the framework — but typed `z.ZodType<unknown, ToolProviderContext>` (input pinned to the same raw shape `getTools` receives), so a schema describing a different shape is a compile error, not a silent drift. Discoverable via `agent.tools.contextSchema`. `combineToolProviders` aggregates constituent schemas into `z.object({ name: source.contextSchema, ... })`.

Optional `ToolProvider.listTools()` is the matching context-free introspection hook for tool _names_ (and descriptions): an inspector has no real `agentId` / `memoryScope` / `toolProviderContext` to offer, so this exists to avoid calling `getTools` with a fabricated context. Skip it when the tool set itself varies by context; a missing `listTools` means "can't introspect," not "no tools." `createToolProvider({ getTools, listTools?, contextSchema? })` forwards it; `combineToolProviders` concatenates each source's summaries (a nested provider's `listTools`, or a plain `ToolSet`'s own keys). The framework never calls it during `agent.run` / `agent.stream`. See `notes/tool-sandboxing.md`.
