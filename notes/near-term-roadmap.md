# Near-term roadmap (post-0.1.0)

**Status:** Draft, for prioritization. 0.1.0 shipped the headless runtime + inspection UI ([`v1-scope.md`](./v1-scope.md)); this file tracks the next wave of **practical usability** gaps — the things a real user hits immediately after the RC — and merges them with everything already deferred elsewhere in `notes/`.

**Legend:** ✅ done · 🚧 partial · 🔲 not started / new ask

Last written: **2026-09-05**.

## 1. Model switching (runtime, settings, and conversation UI)

**Today:** model is baked in once, either on `AgentDefinition.model` or as a runtime fallback via `createAdlRuntime({ defaults: { model } })`, resolved a single time inside `AgentImpl` (`packages/core/src/agent/agent-impl.ts:204`). There is no per-run override field on `AgentRunInput`, no core `ADL_MODEL` env var (only an app-level convention — `apps/playground/src/model.ts` reads `ADL_OPENAI_MODEL`), and the web UI's "Model" section (`apps/web/src/components/app/agent-settings-panel.tsx:56-69`) is a **read-only** projection of `Agent.modelInfo` — there is no mutation path anywhere in the UI today (confirmed: no settings store, no write server function).

**New work needed (this is genuinely new surface area, not a wiring exercise on an existing mechanism):**

| Item                                          | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 🔲 Per-call model override                    | Add `model?: LanguageModel` to `AgentRunInput` / `agent.run(...)` options, threaded through the same resolution point as `agent-impl.ts:204`. AI SDK's `prepareStep` callback (checked against `ai@5.0.188`'s types) already supports returning a different `model` **per step** within one multi-step run — worth threading through as an `AgentRunInput`-level hook once the per-call override lands, rather than reinventing per-step model switching from scratch. |
| 🔲 Mutable "current model" per agent instance | Something like `agent.setModel(model)` or a runtime-level `adl.setDefaultModel(model)` so a swap persists across turns without re-creating the agent. Needs a design decision: is the override per-`Agent` instance (in-process, lost on restart) or persisted (e.g. alongside the inspector session store)?                                                                                                                                                           |
| 🔲 Model catalog / registry                   | The UI picker needs a list of _available_ models to offer, not just the current one. Likely a new `adl.config.ts` concept — e.g. `models: [{ id, label, provider, factory }]` — separate from the `defaults.model` used by `createAdlRuntime`.                                                                                                                                                                                                                         |
| 🔲 Provider-key validation surfaced in UI     | Picker should be able to flag "no API key configured" for a given provider before the user picks it and gets a runtime error mid-conversation.                                                                                                                                                                                                                                                                                                                         |
| 🔲 Web: interactive Model section             | `agent-settings-panel.tsx`'s existing `SettingsSection icon={Cpu}` is the natural insertion point — turn the static `SettingRow` into a `<select>`/combobox wired to a new server function (there's no mutation path today; everything in `apps/web` is read/SSE only per [`inspection-ui.md`](./inspection-ui.md)'s control-vs-data-plane split).                                                                                                                     |
| 🔲 Web: in-conversation swap control          | Either inline in `chat-composer.tsx` (per-turn) or in the settings sidebar (persists across turns) — needs a UX decision, not just a code change.                                                                                                                                                                                                                                                                                                                      |

**Open questions to resolve before implementation:** does a swap apply to the next turn only, or does it change the agent's default going forward? Does it live per-conversation (session-scoped) or per-agent-definition (global, affecting all conversations with that agent)? Both are defensible; the answer changes where state lives.

## 2. Standard tool library: file editing, bash, web search — sandboxed

**Today:** `packages/core/src/tools/` contains only two **adapters** (`createToolFromAgent`, `createToolFromWorkflow`) plus the `ToolProvider` primitives — no built-in tools. The new `packages/tools` (`@agent-dev-lab/tools`, not yet published) now has file-editing tools and a path-jail sandboxing primitive (`createFileJail`); bash/web-search/approval remain greenfield. The only other prior art is `apps/playground/src/tools/knowledge.ts`'s hand-rolled arithmetic evaluator, which deliberately avoids `eval`/`Function` — a one-off, not a framework.

| Item                                          | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ✅ File-editing tools                         | Done, in `packages/tools/src/file/` (new `@agent-dev-lab/tools` package, not yet published): `createFileTools({ root, maxReadBytes?, maxWriteBytes? })` returns `readFile`/`writeFile`/`editFile` tools jailed to `root` (`createFileJail`, `path.resolve` + `fs.realpath`, rejects `..` traversal / absolute paths / symlink escapes). `editFile` is find/replace (unique-occurrence required), not a diff format — decided in favor of the simpler primitive over whole-file overwrite. Parent-directory auto-creation is a known gap, not yet implemented.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ✅ Per-call `tools` override + `ToolProvider` | Done, in `packages/core/src/tools/provider.ts`: `AgentDefinition.tools` and `AgentRunInput.tools` both accept a plain `ToolSet` or a `ToolProvider` (a true interface, `{ getTools(ctx) }`, so a provider can be a class instance), resolved once per call and merged over the runtime/definition tools; `combineToolProviders({ name: source, ... })` merges several **named** sources into one, keyed (not variadic) so the combined context is namespaced — each source only ever sees its own slice, so two unrelated providers can never collide on a field name. `Tools` are still merged flatly via `UnionToIntersection` over each source's contribution. The _stored_ `ExtendedToolProviderContext`'s `toolProviderContext` field is a plain, always-optional key regardless of the context type — an earlier version made a conditional toggle the field's _presence_, which broke widening a concretely-typed `Agent<Concrete, ...>` into the registry type `adl.config.ts` used at the time (`Agent<unknown, ToolSet, unknown>[]`). That registry now widens to `AnyAgent` (`Agent<any, any, any>[]`) instead, which sidesteps the issue entirely, but the field stays plain regardless. `createToolProvider<Context>(fn)` gets the typed generics back for authors. `ToolProvider.contextSchema` is optional introspection metadata (typed `z.ZodType<unknown, ToolProviderContext>` — input pinned to the same context type `getTools` receives, so a mismatched schema is a compile error, not a silent drift; output unconstrained since the framework never parses it) — discoverable via `agent.tools.contextSchema` (e.g. for a settings UI to build a form). `combineToolProviders` aggregates constituent schemas into `z.object({ name: source.contextSchema, ... })`. Dangerous-tools-require-a-sandbox is still to do once `@agent-dev-lab/tools` exists. |
| 🚧 Bash tool                                  | `BashExecutor` interface + `createAsrtBashExecutor` (default) and `createNativeBashExecutor` (non-default, direct `bwrap` on Linux, verified against this repo's dev environment) + `createBashTool` implemented in `packages/tools/src/bash/` per [`tool-sandboxing.md`](./tool-sandboxing.md). No automatic fallback between executors. Still to do: `createNativeBashExecutor`'s macOS (`sandbox-exec`) backend (needs a Mac to build/verify — not attempted unverified), and wiring a `createBashTool` instance into `adl.config.ts`/the playground.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| 🔲 Web search tool                            | Check provider-native tools first (see §3) before building a custom implementation — several providers (e.g. OpenAI, Anthropic) already expose hosted web search as an AI SDK provider tool.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| 🔲 Grep/glob search tools                     | Dedicated `grep({ pattern, path, glob? })` / `glob({ pattern })` tools jailed the same way `createFileTools` is, rather than making the model construct `rg` invocations through the raw `bash` tool. **Checked: ASRT provides no callable search API to build this on** — `RipgrepConfigSchema`/`ripgrep` config is only a knob telling ASRT which `rg` binary _it_ uses internally for its own deny-path scanning, and the one `ripGrep()` helper in its source (`dist/utils/ripgrep.js`) is a private, non-exported, **unsandboxed** `child_process.spawn` used before the sandbox is even set up — not something to import or route model-facing search through. `ripgrep` being a hard runtime dependency of `createAsrtBashExecutor` still means the binary is already required (see [`tool-sandboxing.md`](./tool-sandboxing.md)'s ASRT section), so this tool builds a safe, fixed `rg` argv itself and runs it through the same sandboxed `BashExecutor`/`wrapWithSandboxArgv` path `createBashTool` already uses — a second, narrower consumer of the executor interface, not a new sandboxing mechanism and not an ASRT-provided grep API. Same jail primitive as file tools (`createFileJail`) bounds the search root. Highest-value, lowest-effort addition of this batch — this is what Claude Code, Cursor, and Aider all ship as a first-class tool rather than relying on bash for search.                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| 🔲 `fetchUrl` tool                            | Fetch one specific URL and return its content reduced to readable text/markdown — distinct from web search (which _finds_ pages; this _reads_ one, e.g. a docs page or GitHub file surfaced by search or given directly by the user). Shares the web-search tool's threat model almost exactly (SSRF guard against redirects into internal/private IP ranges, fetched content always treated as untrusted text, never executed) — natural sibling to build alongside it, not new scope.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| 🔲 Todo/plan-tracking tool                    | A `writeTodos`/`readTodos`-style tool (mirrors Claude Code's own `TodoWrite`) so a multi-step agent can externalize and update its plan rather than holding it only in the conversation. No sandboxing concern at all — it's plain per-run state, not filesystem/process/network access — so it doesn't need `createFileJail`/`BashExecutor`-style isolation, just somewhere to persist the list for the run's lifetime (in-memory per call is enough for v1; no store schema change needed). Cheap to build; outsized effect on longer-task coherence, which matters directly for this project's research/eval use case.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| 🚧 Permission/approval gate                   | Sandboxed file + bash tools without an approval mechanism are either always-allow or always-deny. **This pulls forward the approval dispatcher already sketched in [`future-extensions.md`](./future-extensions.md)** (`AdlProjectConfig.approvals.dispatcher`, AI SDK `needApproval` forwarding) rather than treating it as unrelated deferred work — the two features are naturally co-requisites. Scoped to tool calls (not `ctx.requestApproval`) in [`tool-sandboxing.md`](./tool-sandboxing.md); implementation not started.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |

**Shipped as a new `@agent-dev-lab/tools` package** (`packages/tools`, alongside `packages/core` in the existing monorepo layout; `private: true` and changeset-ignored until it's ready to publish), not folded into `packages/core` and not playground examples. Most of the built-in file/bash/web-search tools live there so a project can depend on them independently of the runtime — `packages/core/src/tools/` stays limited to the adapter primitives (`createToolFromAgent`/`createToolFromWorkflow`) plus `ToolProvider` that the rest of the runtime needs directly. `@agent-dev-lab/tools` depends on `@agent-dev-lab/core` (for `Tool`, `WorkflowContext`, `AdlError`), not the other way around. This also gives the approval/sandboxing config (§2's permission gate) a natural single place to live rather than spreading it across core.

**Open question:** grep/glob and `fetchUrl` fit `@agent-dev-lab/tools` for the same reason file/bash/web-search do (they touch the filesystem/network trust boundary). The todo/plan-tracking tool doesn't share that rationale — it's inert per-run state — so it may belong in `packages/core` instead (or as a small standalone example) rather than in the sandboxed package; worth deciding when it's actually implemented rather than assuming it follows the other three.

## 3. Skip tools already provided by the Vercel AI SDK

**✅ Done.** Audited what `ai` / `@ai-sdk/*` actually ship as provider-native tools, checked
directly against this repo's installed packages (`ai@5.0.188`, `@ai-sdk/openai@2.0.109` — the
only model provider installed anywhere in the repo) rather than assumed. `ai` itself ships no
provider tools; `@ai-sdk/openai`'s `openai.tools` does: `webSearch`, `fileSearch`,
`codeInterpreter`, `imageGeneration`, `localShell` (plus deprecated `webSearchPreview`). Full
allowlist/table now lives in [`packages/tools/README.md`](../packages/tools/README.md#provider-native-tools--check-before-building-one-here)
(the package that actually houses the built-in tools this matters for), cross-referenced from
[`tool-sandboxing.md`](./tool-sandboxing.md#web-search-tool). Headline findings:

- **Skip building web search as the primary path** — `webSearch` runs entirely server-side on
  OpenAI's infra and already works with this repo's default `openai(modelId)` factory.
- **`localShell` is not a substitute for the bash tool** — schema-only (confirmed via the
  compiled source: no `execute`), so the calling app still runs the command; adopting it would
  only narrow model support for no safety benefit. Keep `createBashTool` as planned.
- **`fileSearch` is not a substitute for local file tools or the planned `fetchUrl`** — it's
  retrieval over an OpenAI-hosted vector store of pre-uploaded files, not access to the project's
  own filesystem or an arbitrary URL. Flagged explicitly since the name alone looks like a match.
- Grep/glob and the todo/plan-tracking tool have no provider-native equivalent at all — unaffected,
  build as planned.
- `codeInterpreter` and `imageGeneration` aren't on any current roadmap item, but are fully
  server-executed and need zero ADL wrapper if a project ever wants them.
- Scoped to OpenAI only, since it's the only provider installed here — re-run this audit against
  any other `@ai-sdk/<provider>` package before assuming a row generalizes (e.g. Anthropic's own
  `bash`/`text_editor`/`computer` tools are, by reputation, mostly client-executed like
  `localShell` — not verified against installed types in this repo).

## 4. Zod 4 migration

**Risk: low.** Confirmed via grep across `packages/core` and app code:

- Zod is pinned at `^3.25.76` in exactly two files (`packages/core/package.json`, `apps/playground/package.json`); `bun.lock` resolves one shared `zod@3.25.76`.
- `ai@5.0.188` / `@ai-sdk/openai@2.0.109` **already declare** `"peerDependencies": { "zod": "^3.25.76 || ^4.1.8" }` — the AI SDK version already in use supports Zod 4 today, no AI SDK bump required.
- No v3-only risk patterns found anywhere in first-party code: no `z.record()` single-arg calls, no `.email()`, no `zod-to-json-schema` dependency, no custom error-map usage.
- The one thing worth a targeted regression pass: `.default(...)` on workflow **input** schemas (`packages/core/src/workflow/`, several playground/scaffold workflows) — Zod 4 changed some `.default()` output-type inference edge cases.

**Plan:** bump `zod` to `^4.1.8` in both package.json files, run `bun run typecheck` + `bun run test` across the monorepo, and specifically exercise `createWorkflow`'s input-parsing path. Do this **early** — it's cheap, isolated, and best done before §2 adds a pile of new tool input schemas against v3 semantics.

## 5. Run organization & scalability (datasets, tagging, git-hash tracking)

**Today:** runs are a genuinely flat, unindexed list — confirmed at every layer:

- Schema: `adl_workflow_runs` (`packages/core/src/db/schema.ts`) has `workflowRunId`, `workflowId`, `status`, `startedAt`/`finishedAt`, `inputJson`/`outputJson`, `title` — no tags, no arbitrary metadata, no version/commit column.
- Store API: `WorkflowStore.listRuns(filter?: { workflowId?: string; limit?: number })` (`packages/core/src/observability/workflow-store.ts:56`) — the only filter is which workflow and how many; `sqlite-workflow-store.ts:220-231` just runs `SELECT * FROM adl_workflow_runs [WHERE workflow_id = ?] ORDER BY started_at ASC`.
- UI: `workflow-runs-sidebar.tsx` loads the full run set via `useAppLoaderData()` and filters client-side by `run.workflowId === selectedWorkflowId` — no pagination, search, date grouping, or tag filter exists.

This is a **different** flat-list problem than [`workflow-catalog.md`](./workflow-catalog.md), which is about organizing workflow/agent _definitions_. This one is about organizing _run instances_ — and it will bite sooner, since run count grows unboundedly with usage while definition count grows only as fast as authors add code. The two problems likely want a similar mechanism (tags), so they should be designed together rather than twice.

**Three concrete asks, roughly in dependency order:**

| Item                                        | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| ✅ Run tagging / arbitrary metadata         | Done: `adl_workflow_run_tags` side table, `WorkflowRunStartOptions.tags` recorded via the `workflow_started` event, `WorkflowStore.listRuns({ tags })` (any-of match) and `setRunTags` for post-hoc changes, sidebar tag badges + filter box. No `ctx.setTags`/live-event sugar yet (analogous to `ctx.setTitle`) — deliberately deferred as a fast-follow to avoid rippling into every exhaustive `RunEvent` switch in `apps/web` for this first increment. |
| 🔲 Git-hash (or similar) version tagging    | Capture something like the project's git SHA (or a user-supplied version string, for non-git or dirty-tree cases) automatically at run start, stored as run metadata. Lets a user answer "did this behavior change between commit A and commit B?" — currently impossible; nothing in the codebase captures any notion of project version against a run.                                                                                                     |
| 🔲 Datasets of inputs (batch run + compare) | A way to define a named set of inputs for a workflow (or agent) and run all of them — either in one batch invocation or via the CLI — with results grouped for side-by-side viewing. Overlaps in spirit with `adl run <id> --input '{...}'` (`v1-scope.md`), but that's single-input only today.                                                                                                                                                             |

**Scope question to resolve before designing this:** "datasets... for running **and evaluating**" brushes up against `future-extensions.md`'s explicit non-goal ("Built-in evals / scorers — no ADL primitive planned"). Worth deciding up front whether this stays **organizational only** (run N inputs, tag the batch, view outputs side-by-side in the UI — no automatic scoring) or whether it's actually asking to reopen that non-goal. My read of the request is the former — organization/comparison tooling, not a scoring framework — but flagging it since it changes scope meaningfully.

**Prior art worth studying — Weights & Biases:** the parallel the user drew is a good one; W&B's `Run` object already solves a near-identical problem for a similar (ML/research) audience:

- **Tags + groups** on runs (facet + cluster arbitrary run sets) — direct analog to the tagging item above.
- **Automatic git commit SHA + dirty-diff capture** at run start, plus a captured "config" dict per run — direct analog to the git-hash item; W&B's config-capture pattern (snapshot whatever hyperparameters/inputs were used) is also a reasonable model for capturing workflow input at run start (already done here via `inputJson`) plus environment/version metadata (not done).
- **Sweeps** (batch-run a parameter grid, view a results table) — direct analog to the "datasets of inputs" item; W&B sweeps stay organizational (they don't auto-score by default — the user defines what "better" means), which supports treating this as organization/comparison rather than automated evals.

No other tool referenced in this conversation or found in the repo covers this — this is a clean net-new area, same as §1-§4.

## 7. Additional near-term suggestions (not previously tracked anywhere)

- **Usage/cost tracking per agent call** — token counts + estimated cost surfaced in the inspector, most useful paired with model switching (lets a user actually compare cost/quality across models instead of guessing) and with §5's dataset batch runs (compare cost across a batch).
- **Model catalog as a first-class config concept** (see §1) — needed regardless of the UI picker, since there's currently no way to declare "here are the models this project can use" separately from the single default.
- **Provider-key preflight check** — surfaced in both the CLI (`adl run`) and the UI, so a missing `OPENAI_API_KEY`-style failure shows up before a run starts rather than mid-stream.
- **`packages/core/src/agent/agent-impl.ts` needs a refactor.** `AgentImpl#executeTurn` is one ~300-line async function with several levels of nested closures (`withActiveSpan`'s callback wrapping the whole body, `persistResponseMessages` capturing half a dozen outer variables, `streamText`'s own `onStepFinish`/`onChunk` callbacks nested inside that) — genuinely tricky to trace through or safely modify. Worth splitting into named, independently-testable steps (message-loading/system-prompt resolution, tool resolution, the `streamText` call itself, response persistence) rather than one function accumulating local state across the whole turn. Also worth revisiting once split: the cast audit done alongside the `ToolProvider` work (see `tool-sandboxing.md`) found several casts in this file that turned out unnecessary once checked directly — the remaining ones (`StreamTextResult`/`AsyncIterable` erasure around the AI SDK boundary, `TOutput` casts around `outputSchema.parse`) are plausibly load-bearing but weren't re-verified with the same rigor; a structural split might also remove the need for some of them rather than just re-justifying them in place.
